# Cross-language spec fixtures

This directory defines the contracts that govern shared fixtures between the R and Python code.

## The rule

Anything the R and Python implementations must agree on belongs here as a single source. Do not restate the same expectation in the test suite of each language. A hand-maintained per-language copy of a behavior that this directory governs is a review defect because it will drift.

Prose cannot enforce agreement. Every contract added here should be an executable fixture that both suites run, not a description of one.

The rule covers behavior, not implementation. Each package should read idiomatically in its own language, and the two are not expected to match line for line. Before adding a fixture, weigh how often a difference would surface and what it costs when it does.

`normalize_citation()` is the worked example. Each package folds whitespace with its own language's regex, so a quote and a corpus entry differing only by a non-breaking space verify in Python but not in R. That is accepted: the input is uncommon, and the cost is a citation that fails to verify rather than one that verifies wrongly.

## Why this exists

Most Posit R/Python pairs (ellmer/chatlas, ragnar/raghilda, shiny/py-shiny) share concepts and no artifacts. Nothing in them must stay byte-identical. commons is different. Much of its behavior lives in artifacts that must match across languages. The failure mode is invisible. When the system prompt drifts, nothing errors. The agent only behaves differently in one language.

## How each suite consumes these

The Python suite reads this directory directly. The R suite cannot. `testthat` needs its fixtures inside the package, and an installed R package cannot reach files outside its own directory. The R suite reads a copy synced into `pkg-r/tests/testthat/fixtures/shared/`. That copy is committed, `scripts/sync-shared.sh` generates it, and a CI job re-runs the script and fails when the copy is stale.

## What sort of fixtures are here

- **Span names and attributes.** `commons_conversation_turn`, `commons_agent_create`, `commons_data_source_create`, and friends. Also `gen_ai.conversation.id`, `commons.provenance.tag`, and the exact JSON shape of `commons.citation.candidates`. This contract lets `trajectory_read()` read traces from either implementation. Write it so that it survives the conversation-id ownership moving upstream to shinychat.
- **The provenance and citation behavior.** The `derive_provenance_tag()` truth table, `collect_appended_tags()` collection from an exchange's turns, the `build_citation_corpus()` corpus — which text is citable, under which label, and in which order, since matching returns the first entry holding the quote — `normalize_citation()` input/output pairs, `match_citation()` verdicts including both guards (10-character minimum, only-the-quote-verifies), `parse_commons_citation()` well-formed and malformed bodies. Also the chunk-invariance cases of the streaming scanner. The scanner is a pure chunks-in/string-out function, so it is ideal fixture material.
- **System prompt rendering.** The template lives in `prompts/`, not here, but what each renderer makes of it does: `prompt-render.json` holds the data a renderer receives and the prompt it must produce. A shared template pins the words, not the rendering.
- **The system prompt data.** `prompt-data.json` pins the other half: the mapping an agent's sources, definitions, instructions, tools, and model produce, which is what `prompt-render.json` then renders. Cases are declarative source descriptors each suite hydrates into a real in-process DuckDB source, so a difference in how the two packages read a dictionary or a catalog manifest surfaces here rather than in the prompt. The execution tool is the one value in the mapping that differs by language (`run_r` in R, `run_python` in Python), so the fixture carries it as per-language `substitutions`, and a `$execution_tool` token in a case's tools list pins the `has_execution_tool` flag without picking a language. `prompt-render.json`'s tool cases use the same token.
- **Where the citation request lands.** `citation-request.json` pins the reminder to the first tool result of a user turn whose output has to be cited: which value shapes it joins and how, and which turns start a new request. The wording lives in `prompts/citation-request.md`, so the fixture uses a stand-in for it.
- **Handles.** `handles.json` pins the ids a conversation hands out for tool results (`r1`, `r2`, ...), that a value which is not a frame gets one too, the note's opening sentence, and the row cap with the sentence that states it. The opening sentence is pinned as a template with the tool name left as a placeholder, since the tool that reaches a handle is `run_r` in R and `run_python` in Python.
- **Turn reminders.** `turn-reminders.json` pins the wording appended to a user's turn: the concise reminder's text and which model ids earn it, and the restored-conversation reminder as a template plus each package's two substitutions (its language and its execution tool), so the sentence is held once rather than copied per language.
- **The citation dialect and display copy.** The `<citation>` grammar and the `PROVENANCE_DISPLAY` strings, so that both UIs say the same words.
- **The definitions interface.** `definition-export/` holds the shared fixtures: 18 data dictionaries in data-dict's YAML format, each declaring table-level `definitions` whose expressions use data-dict's expression language — 3 valid files (45 definitions) and 15 invalid ones — read by both commons implementations. `definitions.json` pins what both packages agree to produce from them, in four sections:
  - `export_records` — the expected export for each valid definition: its SQL translation, its inferred kind and type, and the columns and definitions it references. Generated from the data-dict binary at the pinned commit by `scripts/generate-definitions-fixture.sh`, which refuses to run against a binary built from anything else. Never hand-edit.
  - `mixed_grain` — a per-definition boolean for `call_metrics`' mixed-grain guard: true when a definition's exported shape is `row` but its expression contains an aggregate, directly or through a definition it references. Absent from data-dict's export (it exists only in the compiler's internal parse tree), so it is hand-maintained and the generator preserves it.
  - `composed` — the composed DuckDB SQL and merged notes for each valid definition: what the compiler produces after inlining a definition's sibling references. Composition is commons' own step, so it is absent from data-dict's export; hand-maintained and the generator preserves it.
  - `invalid` — the data-dict problem code each invalid fixture must produce (e.g. `cycle.yaml` must fail with the cycle error, not a generic parse failure). Hand-maintained; the generator preserves it.

  This fixture does not replace the conformance harness: the harness compares against a real binary, while this pins what both packages agree to consume.
- **Warehouse lowering.** `definition-warehouse-sql.json` pins the Snowflake and Databricks SQL a governed definition compiles to, keyed to the same corpus dictionaries. It differs from every other fixture here in what backs it. The pinned data-dict binary emits `SQL(duckdb)` and R targets only, so there is no upstream output to generate from and no authority to check against: these emitters are commons-only lowering. The fixture is therefore hand-maintained and is the agreement between the two implementations rather than a record of data-dict's. If data-dict ever emits these targets, one upstream implementation could serve both languages and delete both emitters. Cases pin `code` exactly where the whole string is worth reading, `code_contains` or `notes_contain` where a rule is what matters and the full rendering would obscure it, and `composed_code` where the inlining of a referenced sibling is what matters. Its `unsupported` section pins the constructs a target cannot express — a standalone interval, a dynamic `ROUND` scale on Databricks, a nanosecond datetime on Databricks — as `error_contains` refusals alongside the accepted counterpart's `code`, with inline dictionaries rather than corpus keys.

- **Definition expansion and rendering.** `definition-rendering.json` pins what happens to a governed definition after the compiler is done with it: which `{{token}}` queries expand and to what, the one-line gist shown at first touch and in retrieval, and the kind index under a character cap. It carries a bank of export records that each package hydrates into its own shape. A refused query pins the refusal and a reason slug rather than the message, because the wording belongs to each language.
- **Reading a dictionary file.** `data-dictionary-read.json` pins which `data-dict.yaml` files load from disk: a file with no top-level `tables` key is refused rather than read as an empty dictionary, since it gives the agent nothing and is almost always a mistake. The refusal is a slug, since the wording belongs to each language.
- **Table descriptions.** `describe-table.json` pins the SQL-native DuckDB column types shown by `describe_table` and confirms that inspecting the schema does not expose row values. Both suites create and inspect the same real DuckDB table.
- **Catalog rows.** `catalog-rows.json` pins how a warehouse listing becomes relations and columns: which rows are relations at all, what kind each is, which comments count as prose, and where a `DESCRIBE` reply stops being columns. The rows are what Snowflake's `SHOW OBJECTS` and `DESC TABLE`, and Databricks' `system.information_schema.tables` and `DESCRIBE TABLE`, actually return. Running those queries is each language's own business; agreeing on their replies is not. Hand-maintained, since no binary generates it, and booleans travel as strings so the file reads the same from both JSON readers.
- **The catalog merge.** `catalog-merge.json` pins the contract between a warehouse listing and an authored dictionary: the three limits (object cap, prompt threshold, search probe bound), exclusion-glob behavior over bare table names, and merge scenarios — authored prose wins, warehouse types and nullability win, identifier case folds per backend, ambiguity is an error — each with the expected merged tables and definition bindings. Error cases pin a slug rather than message text, because the wording belongs to each language.
- **Definition binding.** `definition-binding.json` pins how a governed definition is bound to the relation a warehouse catalog matched: every column it names, including those inside a `CASE` branch or a `COLUMNS(...)` selection, is lowered with the spelling the warehouse reported, and a physical column named like a sibling reference's marker cannot take that reference's place. A selection from a pattern or from `*` binds as strictly as one written out by name, so a dictionary that documents a column the relation lacks is refused whichever form names it. A selection that matches no authored column is refused too, because it would lower to empty SQL. A dictionary with several faults is refused for the same one in either package: a mixed-grain metric on any table first, then each table in authored order: its match, then every definition's selection, then its columns. Each case reuses `catalog-merge.json`'s dictionary and relation shapes and runs the real merge first. Refusals pin a slug rather than message text, because the wording belongs to each language. Hand-maintained.
- **Catalog access errors.** `catalog-access-errors.json` pins how a failed access probe is read: a SQLSTATE and a message become `authorization`, `transient`, or `unknown`, which decides what the user is told and whether the answer is cached per relation. A case carrying a `sql` field asserts that only the driver's own complaint is read: each suite attaches that statement the way its own drivers repeat it back, and the expected kind stays the one the message alone earns, so a relation cannot classify itself by its name. Hand-maintained, since the cases are the failures real drivers report rather than anything a binary emits. An absent SQLSTATE travels as an empty string, because JSON has no way to spell R's `NA_character_`.
- **Session identity and access precedence.** `catalog-session-changed.json` pins which parts of a warehouse session a refusal reports as changed, so neither package tells a Databricks user that a role moved on a backend that has none. `catalog-access-precedence.json` pins what construction reports when several named relations fail at once: every relation the listing reported is probed before anything is raised, and a name the warehouse never listed is reported ahead of a refusal. Both are hand-maintained, and neither carries message text, since the wording belongs to each language: the session cases travel as snapshot field names, the precedence cases as relation labels and outcome slugs.
- **Relation labels.** `catalog-relation-labels.json` pins the label a selection entry ends up under, which is what the agent sees in a table listing and what every access error names. A confirmed entry is qualified with the connection's namespace only when it named no schema of its own; an entry the warehouse never reported keeps the authored name whole; a relation the warehouse reports without a namespace of its own keeps its bare name, since the label is also the id every later query names it by. Each case names the backend it runs against, because only a Databricks `SHOW TABLES` reply can report a relation with no namespace. The warehouse's own id is kept separately as the relation's identity, since it carries that backend's casing. Hand-maintained. Identifiers are already case-folded, so these cases pin qualification alone and leave case folding to `catalog-merge.json`.
- **Tool registration and descriptions.** `tool-registration.json` pins which tools an agent registers for a given composition of measures, governed definitions and catalog breadth, and what each registered tool tells the model it is for. Registration decides what the model can reach at all, and a description is prompt text it reads before choosing, so both belong here. Arguments are left out: a JSON Schema property and an ellmer type would have to be normalized into each other, which would pin the plumbing rather than what the model reads. The execution tool is left out from the other end, since it is `run_r` in R and `run_python` in Python, so each runner drops the names in `execution_tools` before comparing. Some cases add a warehouse's own semantic models or stubs to a source, which registers the semantic-model half of `call_metrics`. `call_calculation` is listed under `pending_tools` until both packages register it.
- **Skills on offer.** `skills.json` pins which packaged skills `load_skill` offers beside a given set of registered tools: a skill that `requires` a tool is offered only beside it. The list is prompt text the model reads, so both packages must agree on it even before both register every tool a skill requires.
- **The chat theme.** `chat-theme.json` pins the Sass variables the chat theme layers over shinychat's page chat theme, the preset it starts from, and that a caller's own variable beats one of those defaults. The values are what a user sees in the rendered page. Both suites run it. Python reads the theme's Sass in declaration order; R reads the resolved values back with `bslib::bs_get_variables()`, which catches `commons_theme()` drifting from the fixture. Hand-maintained.
- **The execution tool's output.** `execution-repl.json` pins what the model reads back from `run_r` and `run_python` for code that runs to completion: printed text, a trailing value, nothing for an assignment or an invisible or `None` value, stderr, the order of text and value, variables that persist across calls, and the text kept before an error. Each case gives the code in both languages and runs in a real worker. Values print each language's own way, and R keeps the newline that ends printed text when it joins the next output, so cases that show either give per-language text. Three differences are left out on purpose and listed in the fixture: R shows every visible top-level value and Python only a trailing one, R puts two writes to one line on separate lines, and an error is R's condition message but Python's traceback.
- **The worker lifecycle.** `worker-lifecycle.json` pins the worker's time limits (call, interrupt grace, idle) and the tool result the model reads when a call is interrupted, when the worker does not answer the interrupt, and when the worker crashes, and that the programs the worker started, if they stay in its process group, stop when the host closes it or it crashes. The messages are templates with `{language}` and `{seconds}` placeholders, and each case gives the code that causes the failure in each language. Failures only one driver can detect, such as a call the user stopped in Python, are left out.
- **Plots and styled tables from measures.** `measure-rich-results.json` pins what the model and the user get when a measure returns a plot (R's `ggplot`; Python's matplotlib figure) or a styled table (R's `gt`; Python's `great_tables`): the notes the model reads, the plot's alt text, the note when the plot or table cannot be shown, and that a table's handle is its data frame. Each case gives the code for each language and fails for real where it pins a failure. A plot's handle is left out, since R keeps the plot object and Python keeps none.
- **Document artifacts.** `artifact-scan.json` pins how the streaming scanner hands a `<artifact>` element's body to an artifact handler instead of the chat, and what replaces it there. `artifact-edit.json` pins `edit_artifact`'s matching and which documents become a version at all, which is the frontmatter allowlist that keeps model-written YAML away from Quarto options that run code. Errors travel as slugs, since the wording belongs to each language. Only the R package implements documents so far, so only the R suite runs these; `tool-registration.json` lists `edit_artifact` under `pending_tools` until both packages register it.
- **The Posit Connect client.** `connect.json` pins the environment variables each package reads to find Connect and authenticate, which server URL forms reduce to which base URL, and the URL a request goes to for given path segments. A publisher pastes whatever the dashboard shows them, so a URL form that one package accepts and the other rejects would send that package's requests to the wrong place.
- **Typed parameters.** `typed-parameters.json` pins which declared SQL data types a warehouse semantic model's parameters map to, and which values each parameter type accepts. A value the model writes is refused or bound by the same rule in either package. Refusals are pinned as `missing` or `type`, since the wording belongs to each language.
- **Warehouse semantic models.** `semantic-models.json` pins how the semantic models a warehouse defines become names an agent can call: the members the registry lists, the names each member answers to, how a name resolves or fails, whether a metric name belongs to a data-dict definition or a native model when both share a source, the blocks search_pool returns for native members and models, the calls over native metrics that are refused before any SQL runs, what describe_table says about a model, and which models a table's first touch draws context from. An error is pinned by the names its message must mention. Its `error` field names the kind of failure for a reader, and neither suite asserts it.
- **Snowflake semantic views.** `snowflake-semantic-views.json` pins how a Snowflake semantic view is read: the views a `SHOW SEMANTIC VIEWS` reply lists, the model each YAML specification becomes (its public members, typed variables, dependency tables, and context prose), the verified queries it declares, which declared variable types are safe to cast to, the `SEMANTIC_VIEW` query a call over native metrics compiles to, which views a `tables` selection reads up front, leaves as stubs, or drops, and when a listed view is read and kept. R runs the selection and hydration cases against a mocked `DBI::dbGetQuery` and Python against its fake warehouse, both answering from the same listing. The specifications are YAML text, as Snowflake returns them, so each suite's YAML parser is part of what is checked.
- **The live warehouse environment.** `live-warehouse-env.json` names the connection variables both suites read to reach a real Snowflake or Databricks (the vendor's own, which the Python client libraries and `odbc::databricks()` already read), and the schema and objects `scripts/provision-live-warehouse.py` creates there, which the tests use by those fixed names. It is held here because the two harnesses and the script must agree on a name, and a name spelled in two places drifts. Its `env_file` cases pin how both suites read the optional `.env` at the repository root that can hold those variables. It is the one fixture here that pins harness configuration rather than observable behavior.
- **The live warehouse rows.** `live-warehouse-rows.json` holds the three tables a live run is provisioned with, their column types per dialect, and their rows. The tables and columns are the ones the corpus dictionaries in `definition-export/valid/` describe, which is what lets the SQL pinned in `definition-warehouse-sql.json` be executed rather than only agreed on. The Python suite also loads these rows into DuckDB and compares the two engines' answers, so the rows cannot live in the provisioning SQL alone. The R suite does not read them; the warehouse SQL it emits is checked against `definition-warehouse-sql.json` instead. Every value is there because a definition asks about it, and each table's `why` says which. Its `unrunnable` section records definitions whose emitted SQL does not run over a plausible column type, which is a finding rather than a convenience. Generate the provisioning SQL with `scripts/provision-live-warehouse.py`.
- **Trace file naming.** `trace(-[0-9]+)?\.jsonl`, one OTLP envelope per line.
- **The AF_UNIX boundary.** `sandbox-abstract-ipc.json` pins which address-taking socket calls the seccomp network block screens under `network="none"` — `always` for the ones denied outright, `when_addressed` for `sendto`, which stays open with a NULL address because libc spells `send()` that way — the `socketcall` sub-calls that stay allowed on i386, where glibc routes `socketpair()`, `send()`, and `recv()` through `socketcall`, and the Landlock ABI from which the ruleset scopes abstract sockets. It also pins the Landlock ABI from which the ruleset handles the right to reach pathname sockets, and that read roots never get that right. The Python runner checks its filter tables and constants against the fixture; the R runner checks in `sandbox.c` that each `always` call is denied outright and that each `when_addressed` call reads its address first, since an installed seccomp filter cannot be introspected. Hand-maintained.
- **Signals and the worker's process group.** `sandbox-signals.json` pins what a sandboxed worker can reach with a signal, and whether its descendants can leave its process group. The host and the host's process group refuse a signal, a signal to every process has no effect outside the worker, and the worker's own child and process group accept one. Where the sandbox scopes signals (macOS, and Linux with Landlock ABI 6 or later), any other process refuses one too; elsewhere the seccomp filter cannot tell such a process, or one of the host's threads, from the worker's own child, so the case does not run. On Linux, a child also cannot start a session of its own, and a descriptor cannot be told to signal the host; seatbelt has no rule for either, so those cases do not run on macOS. Each case gives the code for each language and runs in a real worker, while a victim process outside the worker listens for a signal that must not be delivered. Every signal sent outside the worker is SIGURG, which is ignored by default, so a failing case leaves the host and the user's other processes running. Hand-maintained.

## Conventions

Fixtures are JSON. If a case genuinely needs a different format, use that format. Each file carries enough structure for a runner to enumerate the cases without hardcoding them. Land both runners together with the fixture, so the authority claim is real rather than aspirational. A runner that enumerates cases must also assert that the set it enumerated is not empty, because an empty fixture otherwise passes.
